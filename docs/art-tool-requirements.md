# Video2Xアートツール化 要件定義書

状態：要件ベースライン v1.0（基本方針を合意済み。実装案と試作時の判断事項を併記）
作成日：2026-09-13。調査対象：このリポジトリのコミット `7db9c18`。
対象読者：制作者と実装担当者。

## 1. 制作の目的と合意状況

動画のアップスケール処理を改造し、モデルのパラメータを意図的に変異させたり、推論にノイズを注入したりして、新しい映像表現を作る。
形状や質感の変化に加え、ユーザーが「step数が極端に低い動画生成みたいな、不気味なぼやけ」と表現する見た目を目標とする。
この表現は視覚的な目標であり、既存モデルへのstep数設定の追加を意味しない。

| ID | 決定 | 状態 |
|---|---|---|
| D01 | 短い映像で試作し、気に入った設定で本番を書き出す | Q1で合意 |
| D02 | モデル由来の形状変化と質感変化を中心に、不気味なぼやけも扱う | Q2で合意 |
| D03 | seedと設定を保存し、同じ環境で再生成する | Q3で合意 |
| D04 | ぼやけの具体像を「輪郭や細部が溶け、形が確定しきらない状態」とする | Q8で採用 |
| D05 | 簡易GUIで調整し、選択区間を再処理してプレビューする | Q8で採用 |
| D06 | 変異を固定するモードと、ゆっくり変化させるモードを設ける | Q8で採用 |
| D07 | 入力と同じ出力サイズを標準にし、モデル対応倍率の拡大も選べる | Q8で採用 |
| D08 | モデル改変で表現が成立するか検証してからGUIを実装する | Q8で採用 |
| D09 | 対象OSはWindowsのみとする | Q9の回答で確定 |
| D10 | 初期版は個人利用向けとする | 追加回答で確定 |

上記を初期版の要件ベースラインとする。
以下の実装方式と数値条件は検証用の案であり、試作で確定する。
初期版はWindows上での個人制作に用いる。

## 3. 初期版の範囲案

まずRealESRGANの同梱モデル一つを対象に、表現が成立するかを検証する。
対応モデルは形式確認後に固定し、モデル名とハッシュを記録する。
対象OSはWindowsのみとし、ローカルで実行する構成を想定する。
Windowsの対応バージョン、GPUとドライバを含む基準環境は試作開始時に記録する。

| 優先度 | 内容 |
|---|---|
| 必須案 | 動画読込、区間指定、元映像との比較、seed固定、レシピ保存と再読込、本番書出し |
| 必須案 | 構造を保った重みの数値変異、推論入力へのノイズ注入、それぞれの強度調整 |
| 必須案 | 形状と質感の変化、および不気味なぼやけについて制作者が採用可能な結果を得る |
| 合意済み | 簡易GUI、固定モード、ゆっくり変化するモード、等倍と拡大の出力 |
| 調査候補 | 中間特徴へのノイズ注入、チャネル減衰、同形状の重みの入替え |
| 初期版の対象外案 | ライブVJ、音声連動、手動キーフレーム、多数の自動生成、モデル学習、拡散モデル導入 |

入力へのノイズ注入だけを実装しても、モデルパラメータ改変の要件を満たしたことにはしない。
既存モデルで表現目標を満たせない場合は試作不成立として記録し、別方式への変更を制作者と判断する。

## 4. 制作フローと操作要件案

1. 動画を読み込み、試作する開始位置と終了位置を指定する。
2. 対応モデルを選び、固定seedで無改変の結果を確認する。
3. 変異方式と強度を調整し、選択区間を処理する。
4. 元映像と処理結果を同じ時刻で比較し、気に入った状態をレシピとして保存する。
5. 保存したレシピを本番区間に適用し、動画と実行記録を書き出す。

| ID | 機能要件 | 確認方法 |
|---|---|---|
| F01 | 開始と終了を元動画の時刻で指定できる | 中途区間でも指定した映像が処理される |
| F02 | 強度、seed、方式を個別に変更し、無改変へ戻せる | 無改変設定で通常処理と比較できる |
| F03 | 重み変異と入力ノイズの強度を別々に設定できる | 一方を0にして各効果を比較できる |
| F04 | seedの固定と再抽選を明示的に操作できる | 強度変更だけではseedが変わらない |
| F05 | GUI案では元映像と結果を並べ、同期再生できる | 同じ元時刻のフレームを比較できる |
| F06 | GUI案では明示的なプレビュー実行と取消を設ける | 取消後の古い結果で新しい設定の表示を上書きしない |
| F07 | 設定を保存して別セッションで再読込できる | 全操作値を復元し、モデル不一致を検出できる |
| F08 | 進捗、失敗理由、出力先を表示する | 失敗した処理を成功と表示しない |

GUIの表示は縮小できるが、最終確認プレビューの推論解像度とタイル条件は本番とそろえる。
軽量プレビューを追加する場合は近似表示と明示し、採用前に本番条件で再確認できるようにする。

## 5. 表現処理の設計案

**重み変異**はモデル構造を維持したまま数値を変える操作とし、元モデルから毎回同じ変異を生成する。
最初の候補は、指定層の重みへの乱数加算または減衰である。
乱数加算では対象層の重みの大きさに応じて強度を正規化する案を検証し、ゼロ値のみの層の扱いも固定する。
層の形状、重みの符号化、対応演算が確認できるまで、任意バイトの書換えを実装方式として採用しない。
変異を繰り返し累積する方式は避け、強度を元に戻すと同じ重みへ戻る設計とする。

**入力ノイズ注入**は推論前の画素を乱数で変化させる操作である。
初期候補はゼロ平均のノイズとし、分布、色チャネルの相関、振幅の単位、値域への収め方を実装仕様に固定する。
現在の変換処理の8ビット画素に直接加算する案では、飽和の影響も比較する。
ノイズの位置は元画像の座標で定義し、タイルの処理順によって模様が変わらないようにする。

**不気味なぼやけ**は輪郭の曖昧さ、細部の溶解、質感の不安定さを評価する表現目標とする。
重み変異や中間特徴の減衰でこの目標に到達できるかは未検証であり、「ぼやけ」スライダーの存在だけを完了条件にしない。
単純なぼかしを比較対象に置き、モデルを介する変化を採用する理由を映像で確認する。

| 時間モード案 | 意味 | 再生成の条件 |
|---|---|---|
| 固定 | 全編で同じ変異重みと入力ノイズ場を使う。出力映像自体は元の動きに応じて変わる | 同じseed、設定、入力位置 |
| ゆっくり変化 | 元動画の時刻から連続的な変調値を計算し、変化幅と周期を操作する | 元時刻を基準にし、区間の切出し位置や処理速度に依存させない |

ゆっくり変化するモードで動かす対象は、試作で重み更新のコストを測って決める。
入力ノイズだけを変調する場合は、その対象を設定に明記する。
固定モードでも元動画に対する時間的一貫性が保証されるわけではなく、不要なちらつきは映像で評価する。

## 6. レシピと再現性の要件案

レシピは人が編集可能なJSON形式とし、スキーマのバージョンを持つ。
作風を他の素材へ適用するためのレシピと、特定の出力を再生成するための実行記録を対応づける。

| 記録先 | 必須記録案 |
|---|---|
| レシピ | 方式とその版、対象モデルのハッシュ、対象層、変異強度、ノイズ設定、seed、乱数方式と版、時間モード、変調対象、周期、位相 |
| 実行記録 | レシピ全文、入力ファイルのハッシュ、選択ストリーム、処理区間、元時刻基準、出力サイズ、色変換、エンコード設定 |
| 実行記録 | 本体と依存ライブラリの版、GPU、ドライバ、演算精度、TTA、実効タイルサイズ、変更後の重みのハッシュ |

同一入力、レシピ、実行環境、実効設定で再生成できることを検証する。
環境差を検出した場合は再現条件が異なると表示し、別GPUでの画素一致は初期版の保証に含めない。
一致判定はエンコード前のフレームを基準にし、コンテナファイルのバイト一致と区別する。
画素一致が得られない実装では、差の原因と測定値を記録し、許容誤差を合意するまで再現性の要件を完了扱いにしない。
区間プレビューと本番の同じ元時刻でも結果を照合する。

## 7. 出力と異常時の要件案

- 等倍出力は推論の倍率とは別に定義し、必要に応じて推論後に指定サイズへ変換する。
- フレームレートと時刻を保持する。可変フレームレートを固定値に変える場合は明示設定とする。
- 初期確認用の入出力は8ビットSDR動画とする。HDRなど未対応条件は開始前に伝える。
- 音声は元の内容と同期を保持する。区間切出しやコンテナ制約でコピーできない場合の再エンコード方針を明示する。
- 元動画と配布モデルは上書きしない。モデル変異は作業用コピーまたはメモリ上で行う。
- 非有限値、ロード失敗、GPUメモリ不足、取消時は処理状態とレシピを残し、不完全な動画を完成品と区別する。
- 白一色や黒一色の結果は制作者が残せるようにする。技術的な処理失敗とは区別して表示する。
- 外部レシピの方式、値域、モデル対応を読込時に検証し、未対応設定を黙って既定値へ置き換えない。

## 8. 試作の受入条件案

評価素材は、人物、細かな模様、動く物体を含む短区間を制作者と選ぶ。
計測用には各5秒、1920×1080、30fpsのSDR素材を提案するが、これは性能実測値や対応上限ではない。

| ID | 判定内容 | 合格条件案 |
|---|---|---|
| A01 | 形状と質感の変化 | 通常処理と並べ、制作者が作品に採用できるレシピを少なくとも一つ選ぶ |
| A02 | 不気味なぼやけ | 元映像、通常処理、単純ぼかしと比較し、制作者が目標に合うレシピを少なくとも一つ選ぶ |
| A03 | 操作による探索 | 同じseedで低強度、中強度、高強度を比較でき、選んだ強度へ戻せる。見た目の単調な変化までは要求しない |
| A04 | 再生成 | 保存、終了、再起動、再読込後に、同条件のエンコード前フレームが一致する。例外は第6節の手順で扱う |
| A05 | 部分処理の一致 | 本番と同じ推論条件で、途中区間のプレビューと本番の対応フレームが一致する |
| A06 | 無改変への復帰 | 全創作効果を0にすると、同条件の通常モデル処理へ戻り、元モデルのハッシュが変わらない |
| A07 | 動画としての成立 | 対象区間のフレーム時刻、出力寸法、音声同期が保たれ、制作者がちらつきを確認する |
| A08 | 失敗と取消 | 不正レシピ、モデル欠落、メモリ不足、途中取消で原因を表示し、元データを保つ |
| A09 | 操作の待ち時間 | 基準環境で初回ロード、単フレーム、5秒区間の処理時間、最大GPUメモリ、取消応答を測り、制作者が許容値を決める |

画質向上指標だけで表現の合否を決めない。
A01とA02は目視による制作者の判断を必要とし、選んだ動画とレシピを受入記録に残す。

## 9. 実装前の調査と実装順序

表現検証をGUI実装より先に行う方針は合意済みであり、各段階の技術方式は調査と試作で確定する。

1. 対象submoduleの固定版を取得し、モデル形式、変更可能な重み、GPU転送とキャッシュ、必要な改修箇所を確認する。
2. CLIまたは検証用呼出しで、無改変、入力ノイズ、重み変異、必要なら中間特徴の変化を比較する。
3. A01とA02で表現を判定する。成立しなければ方式の変更を相談し、GUI開発へ進む条件を見直す。
4. レシピ保存、元時刻に基づく乱数、区間と本番の一致を実装し、A03〜A06を検証する。
5. GUIの配置先を決定して操作画面を実装し、入出力と待ち時間をA07〜A09で確認する。

## 10. 次の判断事項

| 判断 | 推奨案 | 決定が必要になる時点 |
|---|---|---|
| GUIの配置先 | 表現検証後に簡易GUIと既存Qt拡張の工数を比較する | GUI実装前 |
| ぼやけの基準素材 | 制作者が短い参考例または試作結果を選ぶ | A02の判定前 |
| 許容待ち時間とWindowsの対応バージョン、対応GPU | 基準環境の実測を見て決める | A09と対応環境の確定前 |

試作で確認する依存関係は「比較素材→表現方式の採否」「待ち時間の実測→GUI構成」「変調対象→更新コスト」である。
基本方針の合意と表現の実現性検証を区別し、試作結果と残る判断をこの要件ベースラインへ反映する。
