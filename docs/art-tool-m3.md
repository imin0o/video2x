# M3 時間変化と本番動画

2026-09-14。元動画から区間を選び、時間変化を適用して、音声付きの等倍または2倍動画を書き出す処理を追加した。
R14〜R17の実装、技術検証、制作者による受入を終え、M3を完了した。
受入条件A07のちらつきとA09の許容待ち時間は、いずれも承認済み。
同日、実装精査を受けて、区間先頭をまたぐフレームの扱い、成功後の中間動画削除、1回限りの`Session`、進捗イベント契約、段階別計測と画素を変えない高速化を追加し、GPU検証を再生成した。

## 区間指定と書出し

既存のM0基準記録から、GPU、タイル、演算精度を読み込む。
`--input`には本番の元動画を指定する。
各フレームの表示区間（PTSから次のフレームのPTSまで）が、開始時刻を含み終了時刻を含まない指定区間と重なるフレームを選ぶ。
開始時刻や終了時刻をまたぐフレームも含め、表示区間だけを指定区間へ切り詰める。
`--end`を省略すると末尾まで処理する。

```powershell
python -B scripts/art_process.py --recipe build/art/m1-source-color/melt-16/recipe.json --baseline-dir build/art/m2-baseline-2 --input test/test.mp4 --start 0 --end 5 --input-noise 6 --time-mode smooth --period 4 --phase 0.15 --modulation-depth 0.7 --output-scale 2 --output-dir build/art/my-production
python -B scripts/art_process.py --replay build/art/my-production/run.json --output-dir build/art/my-replay
```

出力先には未使用のディレクトリを指定する。
`result.mkv`と同名の`result.json`、実行中から更新される`run.json`、全設定を保存した`recipe.json`が生成される。
成功時は、完成品と記録を保存した後に、その実行が生成した中間動画（`work/*.mkv`と音声結合前の映像）を削除する。
`input.mkv`、JSON、ログ、ハッシュは残す。削除結果は`intermediates`に記録し、削除に失敗しても完成品は失敗扱いにしない。
失敗時と取消時は全部残す。調査用に成功時も残す場合は`--keep-intermediates`を指定する。
削除は処理後に行うため、処理中に必要な最大容量は変わらない。
`--replay`では元動画、区間、設定、環境を復元し、映像の画素ハッシュと音声のPCMハッシュを照合する。
処理スクリプト、CLIとDLL、FFmpeg、Python依存、GPU環境が変わると再生成を拒否する。
コード更新前の記録は、新しい環境でレシピから処理し直す。

## 元時刻と時間変化

元動画のコンテナ開始時刻を0秒とし、各フレームのPTSを有理数で記録する。
`source_timeline`の`time`は変調に使う元PTS、`display_start`と`display_end`は出力に使う切り詰め後の表示区間である。
区間を切り出しても、入力ノイズの時刻と座標は元動画上で変わらない。開始時刻をまたぐフレームも元PTSで変調するため、本番と同じ画素になる。
復号は元動画の先頭から行い、途中シークによる復号履歴の差を避ける。
そのため、後方の区間では先行フレームの復号時間もかかる。

推論用の一時動画にはフレーム順に1秒間隔の時刻を付ける。
時間変調は別に保存した元時刻を参照し、最終出力で元のVFR時刻へ戻す。
中間ファイルは視聴用ではなく、元時刻とフレーム順の照合用に保持する。
プレビューでも元解像度と本番のタイル条件で推論する。

| 設定 | 意味 |
|---|---|
| `time_mode=fixed` | 全フレームで同じノイズ場を使う |
| `time_mode=smooth` | 二つの固定ノイズ場を余弦曲線で補間する |
| `time_mode=smooth-constant` | 補間時の分散を正規化する既存の試作モード |
| `modulation_depth` | 補間幅0〜1。0では固定と一致。既定値1で従来の動作を維持 |
| `period` / `phase` | 周期は秒、位相は周期に対する割合 |
| `modulation_target` | `input_noise`のみ。重みと特徴は時間変調しない |

2 passの場合は元寸法へ戻してから無改変モデルへ再入力する既存の順序を保つ。
等倍指定でも推論は2倍で行い、色の仕上げ後にLanczosで元寸法へ戻す。
等倍出力の原像保持量は寸法変換後に適用し、保持量1では元の画素に戻す。

## 映像と音声の出力契約

対応入力は正方画素の8ビットSDR、RGBまたはBT.601／BT.709系の色変換とする。
HDR、未対応画素形式、未対応の色行列は開始前に拒否する。
YUVの色行列が未指定の場合はBT.601として変換する。
出力はフルレンジBGRの可逆FFV1、Matroska形式になる。

出力の0秒は指定した開始秒で、開始時刻をまたぐフレームは0秒から表示する。
元動画に映像がない時間は埋めない。映像の開始が指定した開始秒より後なら、その差を維持する。
隣接区間`[a,b)`と`[b,c)`は有理数の表示区間では隙間も重複もなく分割される。
Matroskaの時刻は最寄りの1msへ丸め、元の有理数時刻もJSONへ保存する。ファイル同士の境界には、この丸め誤差が残る。
丸めにより二つのフレームが同じ時刻になる区間は失敗として検出する。
全フレームの画素、時刻、寸法に加え、最終フレームの表示終了時刻を確認してから完成品にする。
FFmpegがコンテナの既定フレーム長を整数msへ切り下げる場合は、末尾時刻の差を1msまで許し、指定値と復号値を両方記録する。

`--audio pcm`が既定値で、全音声トラックを同じ元区間で切り、PCM float32に変換する。
圧縮音声のパケット境界に依存せずに切り出すため、音声のストリームコピーは行わない。
サンプルレートとチャネルを維持し、映像に対する遅延も保持する。
復号したサンプル数と先頭、末尾の時刻を元音声と照合する。
`--audio omit`で音声を明示的に除外できる。

## 進捗と取消

共通APIの`Session(on_progress=callback)`で進捗イベントを受け取る。CLIは同じイベントをJSON行で標準エラーへ出し、`run.json`も更新する。
コールバックは処理スレッドで同期的に呼ばれる。GUIは画面更新を自身のUIスレッドへ配送する。

| キー | 意味 |
|---|---|
| `run_id` | 実行記録と同じID |
| `stage` | `prepare`、`decode-source`、`input-transform`、`inference`、`verify-inference`、`reinput-resize`、`output-transform`、`encode-output`、`mux-audio`、`verify-output`、`verify-audio` |
| `pass_index` / `pass_count` | 推論と再入力の段階のpass番号と総pass数。その他の段階では`pass_index`は`null` |
| `completed` / `total` / `unit` | 処理済み数、総数、単位（`frames`または`streams`）。不明な値は`null` |
| `total_exact` | 総数が確定値か。`decode-source`は平均fpsによる推定値で、VFRでは超えることがある |
| `elapsed_seconds` | 実行開始からの経過秒 |
| `state` | `running`、または終了を表す`completed`、`failed`、`cancelled` |

推定の総数に達しても完了ではない。終了は`state`が`running`以外のイベント1件だけで判断する。
CLIは同じ段階の進捗を1秒ごとに間引くが、段階の切替と終了イベントは必ず出す。

`Session`は1回の実行専用で、成功、失敗、取消のいずれの後も再利用すると`RuntimeError`になる。GUIは実行要求ごとに作成する。
開始前に届いた取消は有効で、`cancel()`を繰り返しても最初の要求時刻を保持する。経過時間は生成時ではなく実行開始から測る。
GUIからは別スレッドの`Session.cancel()`で取り消す。CLIではCtrl+Cが同じ取消になり、2回目のCtrl+Cは即時中断になる。
取消時は子プロセスの終了を待ち、`cancelled`と取消応答時間を保存する。
失敗時は`failed`、理由、推論ログの末尾を記録する。
失敗時と取消時も、子プロセスの終了後に元動画のハッシュを照合し、`source_preserved`に記録する。
出力は検証完了まで`.partial.mkv`とし、失敗や取消で`result.mkv`を作らない。

`run.json`の`timings`には、段階と操作ごとの累積秒を記録する。
操作は、`decode`（処理用の復号と画素形式変換）、`pixel`（画素処理）、`encode`、`pixel_hash`（書出し前の画素ハッシュ）、`verify_decode`と`verify_hash`（書出し後の復号照合）、`file_hash`、`subprocess`（推論CLIとFFmpeg）に分ける。
`setup`は区間処理の開始前に行う、基準記録と環境の検査である。ハッシュ一覧の比較自体は計測上無視できるほど短いため、照合の費用は`verify_*`で表す。
入力段と出力段の変換では、最大8フレーム（CPU数が少なければその数）を並列に処理する。この段の`pixel`は、画素更新と書出し前ハッシュの結果を待った実時間である。
各フレームの処理は他フレームに依存しないため、並列化しても画素は変わらない。FFV1の中間ファイルはフレームスレッドで復号し、元動画は既定の設定で復号する。


単体検証には、非フレーム境界の区間、隣接区間による表示時間の分割、1フレームより短い区間、0でないコンテナ開始時刻、VFRの長い表示間隔、映像のない区間、複数音声、AAC、遅延音声、元PCMサンプルとの一致、等倍での原像復帰を含める。
`Session`の再利用拒否と開始前の取消、進捗イベントのキーと終了イベント、成功後に削除する中間動画の範囲も単体で検証する。
GPU検証では本番5秒と途中プレビューの画素照合、成功後の中間動画削除、2 pass、再起動後の映像と音声の一致、取消と例外後の再生成を確認する。
メモリ不足はGPU処理後に`MemoryError`を注入する試験であり、実GPUのメモリを枯渇させる試験ではない。
GPU検証は全項目成功した。[結果JSON](../build/art/m3-verified-2/summary.json)。
本番の300フレームに対して、2.017秒をまたぐフレームを含む途中5フレームが推論直後と最終出力の両方で一致し、VFRの2 passでも対応6フレームが一致した。
末尾検証では、0.9秒のフレームが0.965秒から、0.967秒のフレームが0.97秒まで切り詰められた。
取消と注入例外の後、失敗記録に中間動画と元動画の一致が残り、別Pythonプロセスへの再起動後にも20フレームと音声のハッシュが一致した。
本番5秒の最終画素と音声は、改修前の[先行検証](../build/art/m3-verified/summary.json)と全300フレームで一致した。

## 実測と制作者の確認

測定環境はWindows、RTX 4070 Ti SUPER 16GB、ドライバ610.62、タイル200、TTA無効。
入力は`test/test.mp4`の1920×888、60fpsで、本番5秒は3840×1776の300フレームへ出力した。
採用済み`melt-16`に入力ノイズ6、周期4秒、位相0.15、変調幅0.7を設定し、同じ条件の検証を改修前後で1回ずつ測った。

| 測定対象 | 改修前 | 改修後 |
|---|---|---|
| 5秒の本番出力全体 | 441.2秒（7分21秒） | 210.0秒（3分30秒） |
| 単フレームの等倍出力全体 | 3.90秒 | 4.00秒 |
| 本番のモデル読込 | 170.9ms | 167.9ms |
| 本番の初回フレーム推論 | 113.9ms | 111.0ms |
| 2フレーム目以降の平均推論 | 105.8ms | 103.8ms |
| 本番の出力エンコードと音声処理 | 21.96秒 | 17.02秒 |
| GPU推論中の取消応答 | 38.8ms | 39.3ms |
| GPUメモリの観測最大値 | 本番2237MiB、単フレーム2406MiB | 本番1650MiB、単フレーム1646MiB |

全体時間には、元動画の復号、ノイズと色の処理、中間動画の可逆圧縮、画素の照合を含む。
GPUメモリ値は200ms間隔で測ったデバイス全体の使用量で、他アプリを含み、プロセス単独の厳密なピークではない。
出力の指定末尾は5秒、FFmpegの整数msによる復号末尾は4.999秒、音声は44.1kHzの220500サンプルだった。
本番出力の保存容量は、成功後に中間動画10.44GBを削除して1.72GBになった。

改修後の段階別の累積秒は次のとおり。改修前の内訳は、計測だけを追加した[段階別計測](../build/art/m3-timing-1/run.json)に残した（全体415.8秒）。

| 段階 | 改修前 | 改修後 | 主な内容 |
|---|---|---|---|
| `inference` | 113.7秒 | 106.5秒 | 推論CLI全体。GPU推論は約31秒で、残りの大半はCLI内の4K FFV1書出し |
| `output-transform` | 169.1秒 | 42.2秒 | 4Kでの色の仕上げ、復号、書出し、照合 |
| `encode-output` | 22.2秒 | 14.1秒 | 最終映像の書出し |
| `input-transform` | 44.6秒 | 11.5秒 | 入力のぼかしと時間変調ノイズ |
| `verify-inference` | 37.6秒 | 11.3秒 | 推論出力の復号照合 |
| `decode-source`ほか | 24.2秒 | 17.5秒 | 元動画の準備、音声結合、最終照合 |

短縮は、FFV1中間ファイルのフレームスレッド復号、変換段のフレーム並列処理、推論出力の二重復号の統合、元動画ハッシュの開始時と終了時への集約による。
